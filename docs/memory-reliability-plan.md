# OneLedger 记忆可靠性改进计划

## 目标与边界

继续使用 `global / project / personal` 和仓库名 `scopeId`，保留同一作用域整篇覆盖的语义。Agent MCP 仍只提供 search、remember、forget、list、get；原始 inbox 和 secret 只由管理台处理。桌面运行与验收使用 Tauri。

## 第一阶段：写入必须可信

- `remember` 明确返回 `stored / queued / rejected / unchanged / conflict / error` 状态、命中规则类型和安全位置。不能通过 `redacted: true` 猜测是否写入成功。
- 完整匹配、可验证已经移除的凭据允许以脱敏版写入；私钥块不完整、泛化的高熵命中等仍拒收。拒收正文只保留安全替换文本。
- 蒸馏覆盖接受可选 `expectedRev`。调用方提供时，数据库必须原子校验旧版 rev；不匹配返回冲突与当前 rev，保留原文和现有记忆。首次创建使用 rev 0。
- 晋升与删除 inbox 在同一事务内完成；数据库失败不得返回成功，也不得丢掉 inbox。
- TypeScript 与 Tauri Rust 扫描规则保持一致，尤其检查 UUID、路径和高熵误杀。

## 第二阶段：采集和蒸馏形成闭环

- 采集按来源、作用域和内容指纹去重，重扫不再追加同一份原文。保留约定文件、会话摘要、`.workbuddy/memory` 的白名单和现有目录排除。
- 管理台按来源、项目和时间显示待蒸馏材料，优先呈现高信号材料；支持选择材料、编辑整篇摘要、写回对应作用域，并在成功后确认已处理材料。失败时材料保持待处理。
- 管理台可以查看拒收原因及数量；为拒收记录和审计事件提供受控保留策略。清理前须保留汇总计数，避免失去可观测性。

## 第三阶段：召回

- SQLite 检索采用 FTS5 索引、相关度排序及中文可用的切词策略，保留作用域过滤与权限过滤。迁移需支持既有数据库重建索引。
- MCP 初始化可提供简短使用说明和当前作用域索引，但不能假定服务端 cwd 是客户端仓库，也不能假定客户端会把初始化说明注入模型。项目名必须由客户端显式提供，或通过受支持的 roots 协商获取。
- 用中文短语、英文关键词、跨作用域与无权读取内容验证召回效果和安全边界。

## 验收

运行 TypeScript 检查与测试、Rust 检查与测试；检查中文文件保持 UTF-8 且没有乱码或意外转义。使用 Tauri 管理台验证队列和写入状态，并通过 Agent MCP 自行调用 remember、get、search 验证真实返回。

## 当前实现与后续集成

- 已实现明确写入状态、命中规则与行号、可完整替换凭据的片段脱敏；泛化高熵和不完整私钥继续拒收。管理台拒收视图只展示规则，不展示正文。
- 已实现 `expectedRev` 校验；已有记忆在缺少 `expectedRev` 时拒绝覆盖。Tauri 和 TypeScript 的晋升使用事务；数据库写入失败保留 inbox。
- 已实现采集内容去重、队列分页和 WorkBuddy 优先排序。管理台可选择同一作用域的材料、编辑整篇记忆并确认处理。原始 inbox 不开放给 Agent。
- 自动生成蒸馏正文尚未实现：当前 `distill.provider=none`，现阶段由管理台操作者整理正文。后续若接入模型，需要在管理员侧完成模型配置、完整脱敏验证、失败重试与来源确认，不能借此开放 Agent 的原始 inbox 权限。
- 已实现管理台手动清理 90 天前的拒收记录与脱敏事件；清理时先按日期、规则类型汇总归档事件。正式记忆与未蒸馏材料不自动删除，升级不会自动清理历史数据。
- 已实现 FTS5 trigram 检索与相关度排序；中文三字及以上短语使用索引，短查询回退到 `LIKE`。PostgreSQL 保留原检索路径。
- Tauri HTTP MCP initialize 提供全局索引与调用提示；客户端若在初始化参数里提供仓库名 `projectScopeId`，也会带上该项目索引。TypeScript MCP 提供调用提示。是否将初始化说明放入模型上下文仍取决于客户端。后续需要针对目标 Agent 客户端实现并验证项目识别与自动调用；服务端不会猜测客户端 cwd。

## 下一阶段：实施顺序与完成条件

以下工作按顺序实施。每一步同时更新 Tauri Rust 路径和 TypeScript 服务路径；涉及数据结构时，先完成迁移和回滚测试，再接入管理台。保持现有作用域、整篇覆盖和五个 Agent MCP 工具不变。原始 inbox、蒸馏草稿与 secret 仍只允许管理台访问。

### 1. 让采集去重跨越 inbox 生命周期

**现状。** `find_collected_inbox` 只查询尚留在 inbox 的正文。管理台确认后会删除来源行，因此未变化的文件在下一轮采集时可能再次入队。

**实现。** 在 `src-tauri/src/db.rs` 和 `src/db/sql.ts` 增加独立的采集指纹表及版本迁移。每条指纹记录采集器名称、稳定的来源键、`scopeKind`、`scopeId`、内容摘要、扫描规则版本、首次和最近见到的时间，以及最近处理状态。来源键采用规范化文件路径或会话标识，只用于采集去重；项目 `scopeId` 继续只用仓库名。内容摘要由本地计算，表中不保存原始秘密正文。给来源键、作用域、摘要和规则版本建立唯一约束。

在 `src-tauri/src/collect.rs`、`src/collect/runner.ts` 的采集入口先检查指纹，再进入 `remember`。首次见到的新版本与 inbox 写入在同一事务内登记；写入失败不得提前记录为已采集。已存在且内容未变时仅更新最近见到时间，不新建 inbox；内容变化时保留旧处理记录并允许新版本入队。被拒收的版本也记录指纹，避免每半小时重复产生拒收和脱敏事件；扫描规则升级后通过规则版本重新评估。仅对能够准确还原来源键的旧数据回填，不能准确回填的历史条目不猜路径、不删除。

**验收。** 同一文件连续扫描、蒸馏确认后再扫描、拒收后再扫描均不增加 inbox 或脱敏事件；修改文件后恰好产生一个新版本；重启后仍有效。项目作用域始终是仓库名，采集白名单和排除目录保持不变。

### 2. 原子完成管理台蒸馏确认

**现状。** `/api/inbox/resolve` 先调用 `remember` 提交正式记忆，再逐条删除所选来源。删除中途失败会使正式记忆与队列状态不一致。单条 `promote_inbox` 已有事务，但不能覆盖这个多来源管理台流程。

**实现。** 在 `src-tauri/src/service.rs` 和 `src/memory/service.ts` 增加单一的“确认所选来源”服务操作，由两端 `/api/inbox/resolve` 调用。事务内重新读取并校验全部来源 ID：必须存在、状态为 `proposed`、不含 secret、属于同一作用域，且 ID 不重复；随后扫描管理员编辑的标题与正文，在同一事务内校验 `expectedRev`、写入或确认未变化的正式记忆、写审计、删除全部选中来源。把现有覆盖逻辑抽成可在事务内复用的内部操作，避免嵌套事务。数据库层再次检查版本；已有作用域缺少 `expectedRev` 时返回冲突，不能依赖事务外的预检查。只在提交成功后返回 `stored` 或 `unchanged`；冲突和任意写入失败都保留正式记忆与全部来源原状，并返回当前 rev 或明确错误。

**验收。** 注入第二条来源删除失败、审计写入失败和并发 rev 变化，验证整笔回滚；重复提交已成功的请求不覆盖新版本，也不把部分成功误报为完整成功。Tauri 管理台上验证选中、编辑、提交、冲突提示和队列数量。

### 3. 移除读取触发的记忆清理

**现状。** `search/get/list` 会调用 `retire_non_distilled`，Tauri 启动时也会调用它；读取或启动因此可能改变旧记忆状态，相关错误还可能被忽略。

**实现。** 删除上述自动调用。Agent 可见性过滤继续只返回正式蒸馏记忆，不靠先执行 `forget` 达成；管理台仍可看见需要整理的旧条目。若要清理历史碎片，提供管理员侧明确的预览和一次性迁移：列出数量、作用域及将受影响的 ID，确认后在事务内改状态、写审计与迁移标记。迁移不得删除正文，失败回滚，重复运行不重复修改。不要把维护操作挂在 MCP 查询或启动流程上。

**验收。** 对有旧碎片的数据库调用 search、get、list 并重启 Tauri，记忆行的状态、rev 与更新时间均不变；Agent 仍看不到未蒸馏碎片。维护迁移单独验证预览、幂等与回滚。查询审计可继续追加，但审计失败不能悄悄改变记忆内容。

### 4. 把蒸馏变成可跟踪的管理台任务

**实现。** 采集完成后按作用域聚合待处理材料，在 Tauri 管理台显示新增量、最旧等待时间、高信号来源和最近一次处理结果；对已被指纹跳过的重扫不重复提醒。先提供“待蒸馏”任务与人工编辑流程，让 `distill.provider=none` 时也有稳定出口。若配置了模型提供方，仅在管理员侧生成草稿：按作用域分批读取安全材料，记录来源 ID 和生成时的 `expectedRev`，限制输入长度，要求模型输出整篇摘要；草稿保留待审核，不自动晋升为正式记忆。审核提交复用第 2 步的原子确认操作；来源、rev 或扫描状态变化时标记草稿过期并要求重审。记录生成失败原因、有限次数重试和人工重新发起入口，不向 Agent 增加 inbox 工具。

**验收。** 新材料出现后管理台能找到对应任务；无模型配置时可完整手工处理；模型失败或关闭窗口不会丢来源；草稿未经审核不会进入 search/get；审核时若 scope 已被另一个 Agent 更新，返回冲突并保留草稿和来源。

### 5. 验证主动召回与检索质量

**客户端集成。** 先确定实际使用的 Agent 客户端，验证其是否会把 MCP initialize 的说明交给模型，以及是否支持可靠传入当前仓库名。能提供仓库名时使用项目索引和 `memory.get(scopeKind=project, scopeId=仓库名)`；不能提供时明确展示当前能力边界，并在受支持的客户端适配层触发 get。全局记忆按需读取。服务端不推断自己的 cwd，也不把路径当 `scopeId`。整个流程继续使用已有五个工具。

**检索评测。** 建立不含真实秘密的中文、英文、双语、两字短词和跨作用域查询集，逐条标注应命中的文档及不应出现的文档。记录命中率、前五条命中率、误召回和延迟的基线；对三字以上 trigram 检索与短词 `LIKE` 回退分别测量，并覆盖 PostgreSQL 路径。只有评测显示短词性能或相关度不足时，再调整分词或索引；保留权限和敏感级别过滤，不直接引入向量库。回归验收要求标注查询不退化、secret 零返回，且性能达到测试机器上记录的目标值。

### 6. 给脱敏版入库加二次验证

**实现。** 对准备写入的标题和正文再次扫描替换后的文本；若仍命中凭据或无法证明完整替换，则拒收并返回安全的命中类型与位置。用完整和不完整私钥、多行凭据、令牌、中文路径、UUID 及普通高熵文本建立两端共享的回归样本；升级扫描规则时提高采集指纹的规则版本，让旧材料可重新评估。测试与日志只保存脱敏样本，不放真实凭据。

**验收。** 可完整移除的凭据只留下脱敏版；残留和不完整凭据不能进入正式记忆；正常 UUID、路径和普通文本不被误拒；Rust 与 TypeScript 对同一组样本给出一致状态。

## 第二阶段实施记录（2026-09-23）

步骤 4（蒸馏任务化）已完成并在真实环境验证：

- **数据层（schema 6）。** 新增 `distill_drafts` 表：作用域、标题、正文、来源 ID 与来源指纹（`id:sha256(title\nbody)`）、生成时的 `expected_rev`、provider/model、状态（pending / stale / failed / discarded）、过期原因、错误、尝试次数与时间戳。两端迁移幂等。
- **任务聚合。** 新增 `src-tauri/src/distill_job.rs` 与 `src/memory/distillJob.ts`。`tasks()` 按作用域聚合待处理材料，输出待处理条数、最旧等待时间、高信号（WorkBuddy）条数、来源样本与上一条草稿状态。所有聚合在 SQL 内完成（`GROUP BY` + 窗口函数），固定 3 次查询、与作用域数量无关。
- **草稿生成（仅管理员侧）。** 只把通过安全扫描的材料送入模型：secret 级或扫描后仍命中 secret 的材料直接排除并回报 `blocked`；每作用域最多 12 条、单条 4k 字符、总量 24k 字符；prompt 要求整篇覆盖并禁止编造。草稿落库为 `pending`，**绝不自动晋升**。失败记录原因与尝试次数，同一作用域连续失败满 3 次后要求人工重新发起。
- **过期与审核。** `mark_stale_if_changed` 在返回任务前检查来源存在性、来源内容指纹与作用域 rev；变化则标记 `stale` 并要求重新审核，来源与草稿都保留。审核提交复用第 2 步的原子确认（`confirm_sources` / `confirmSources`），因此作用域被其他 Agent 推进时返回 conflict，不会覆盖。
- **管理台。** 「蒸馏队列」拆为「待蒸馏任务」与「材料明细」两个子视图。任务视图显示作用域、待处理条数、最旧等待、高信号数、草稿状态与最近结果，支持生成/重新生成草稿、废弃草稿、按作用域筛选与分页（每页 20，超出显示「还有 N 个作用域」）。`distill.provider=none` 时隐藏生成按钮并提示手工整理，手工路径完整可用。
- **接口。** 两端新增 `GET /api/distill/tasks`、`POST /api/distill/draft`、`POST /api/distill/draft/:id/discard`。Agent MCP 工具集未变，草稿与来源不通过 MCP 暴露。
- **验证。** tsc（服务端 + web）通过；vitest 10 个文件 46 个测试；cargo 19 个测试。Tauri 窗口实测：面板显示 925 个作用域 / 32659 条待处理并正确分页；对 1 条材料的作用域生成草稿 → 审核表单回填模型正文 → 确认写入后统计降为 924/32658，Agent 随即能通过 MCP 读到该记忆；未审核草稿对 `memory.get`/`memory.search` 都不可见。用本地 stub 兼容服务验证 `provider=openai-compatible` 全链路，随后复位为 `none`。
- **验收中发现并修复的缺陷。** 原始实现用 `LIMIT 5000` 拉全部待处理行再内存分组，工作台恰好有 5000 条积压，导致新入队材料和整个 global 作用域被静默丢弃；改为 SQL 聚合后又暴露出逐作用域 N+1 查询，925 个作用域直接拖死连接（接口无响应）。两处均已修复为常数次查询，并加了 300 作用域的性能回归测试。
- **待办（第 5、6 步）。** 主动召回验证与检索评测尚未开始；存量数据里有 925 个历史路径型 `scopeId`（2026-09-20 之前的采集写入，新采集已不再产生，实测新增 0 个），按第 3 步要求不做自动清理，需要时由管理员显式维护。

## 第三阶段实施记录（2026-09-23）

### 步骤 6：脱敏版入库二次验证

- **实现。** 两端新增二次验证入口（Rust `scan::verify_redacted`、TS `verifyRedacted`）：对**替换后**的标题与正文再次扫描，命中非空即表示替换不完整或无法证明完整，必须拒收。接入四条写入路径：`remember` 直写、`remember` 拒收分支、管理台 `confirm_sources` / `confirmSources`、以及蒸馏送模型前的 `safe_sources`（残留材料与 secret 一样排除，不给模型）。
- **拒收返回。** 报告命中类型与行号（`type` / `line` / `field`），只描述规则，不返回正文。管理台拒收视图继续只显示规则。
- **两端共享回归样本。** Rust 与 TypeScript 各自内置同一组 12 条样本（完整私钥、不完整私钥、令牌、多行凭据、中文路径、UUID、sha256 摘要、普通文本），并断言两端给出**一致**的敏感级别与"替换后无残留"。另断言脱敏标记本身（`[REDACTED:*]`）不会在二次扫描中自我触发。
- **实测。** 真实 MCP 调用提交含未闭合私钥标记的正文，返回 `status: rejected`、`hits: [{type: private_key_incomplete, line: 2, field: body}]`；普通内容随后写入成功（rev 9 → 10）。正常 UUID、中文路径、sha256 摘要、普通中英文文本均不被误拒。
- **规则版本联动。** 采集指纹的 `SCAN_RULES_VERSION` 为 1；后续提高该值时旧材料会被重新评估（第 1 步已实现，见 `src-tauri/src/util.rs` 与 `src/types.ts`）。

### 步骤 5：召回与检索评测

- **评测集与脚本。** 新增 [retrieval-eval.md](retrieval-eval.md) 与两个可执行脚本：`scripts/retrieval-eval.ts`（6 篇语料 + 11 条标注查询 + 5 项边界断言）、`scripts/retrieval-perf.ts`（5000 篇规模延迟）。两者都用独立临时库，不触碰用户数据，语料不含真实凭据。
- **基线结果。** 命中率 11/11 = 100%，P@5 = 100%，误召回 1 条（两字短词「约定」同时命中两个含该词的标题，属 `LIKE` 子串的预期行为）。边界 B1–B5 全 PASS：secret 零返回、pii 零返回、未蒸馏材料零返回、不存在词零返回、作用域过滤生效。
- **延迟基线（5000 篇）。** trigram 三字以上 6.2ms、五字 6.0ms、中文+数字 2.6ms；`LIKE` 两字短词 4.8ms（最大 11.9ms）、高频短词 2.1ms。均在毫秒级，**不调整分词或索引，不引入向量库**。
- **客户端集成。** 自行连接本机 MCP 完成验证：`initialize` 携带 `projectScopeId` 时返回全局与项目索引（实测返回 `global:*` 与 `project:OneLedger` 条目），`tools/list` 仍为 search / remember / forget / list / get 五个工具；`memory.get` 按 `scopeKind=project, scopeId=仓库名` 正确召回。服务端仍不推断自身 cwd，`scopeId` 只接受显式传入的仓库名。
- **未完成项。** PostgreSQL 检索路径无可用实例，未做实测；后续需在真实 PG 部署上复跑同一评测集。是否把 initialize 说明注入模型上下文仍取决于具体客户端。
